# Приёмка Agent_Allish — что запускать и что нельзя считать доказанным

## Раздельные режимы
- **manual:** LLM читает YAML и формирует результат вручную; это не отдельный программный вызов модуля.
- **mock:** фиктивные данные и согласования только для изолированного теста; нельзя засчитывать как согласие владельца.
- **live:** реальный пользователь, реально доступные источники и подтверждённые записи; каждый факт вызова подтверждается журналом.

## Минимальный тест исполнения
1. Создать новый **синтетический** кейс, явно обозначенный synthetic; не загружать пользовательские материалы в репозиторий.
2. Прочитать AGENTS.md, MODULE/EXECUTOR, contracts, workflow, routing и выбранные methods; записать точные пути и версии.
3. Подтвердить бриф **реальным** сообщением пользователя; зафиксировать идентификатор и ревизию.
4. Выполнить один `run_next_stage`, сохранить запрос/ответ, stage/method records, ссылки на источники и подтверждение записи.
5. **Негативный тест:** вызвать переход без `approve_stage` или с mock-approval. Ожидаемый результат — отказ, следующий этап не запускается.
6. Получить действительное согласие именно на эту версию этапа, затем проверить переход ровно на один этап.
7. Остановить сессию, открыть другой чат/контекст и попытаться продолжить по сохранённым `brief.json`, `state.json`, ревизиям, манифесту и подтверждениям. Если среда не поддерживает это — статус `not_verified`.
8. Отдельно изменить ревизию или удалить файл; восстановление должно блокироваться без реконструкции фактов.

## Проверка контрактов
При доступном Python 3 и `jsonschema>=4`:
```bash
python -m pip install 'jsonschema>=4'
python validation/validate_case.py /path/to/cases/synthetic_case
```
Скрипт проверяет распознанные JSON по Draft 2020-12 и совпадение case_id. Он **не** проверяет все семантические связи, методические `outputs.required`, фактическое происхождение данных, согласования и физическую доступность заявленных ссылок. Эти проверки обязательны отдельно. Отрицательные тесты: неправильный `case_id`, отсутствие обязательного поля, несовместимый `revision`, несуществующий источник/файл, фиктивное согласование и неподтверждённое рекламное обещание.

## Проверка содержания
- Не менее двух реально присутствующих клиентских проблем; при единственной проблеме не выдумывать вторую.
- Все KPI: baseline, целевое значение, период, сценарий, gap и статус.
- Экономика: сравнение с BAU, независимая чувствительность цены/конверсии/затрат, честные неизвестные.
- Сообщения C04/C05: подтверждённое свойство либо маркированная гипотеза, без недоказанных обещаний.
- Два полноценных DOCX, а дополнительный формат — только если он требуется брифом; сверка с исходными этапами.
- Повторить на другом **синтетическом, не телеком** кейсе, чтобы избежать подгонки.

## Отчёт о проверке
Для каждого шага: `executed / simulated / not_run`, вход, ожидаемое поведение, наблюдаемый результат, путь к доказательству, ограничения. Ни один тест нельзя считать пройденным только потому, что его инструкция написана.
