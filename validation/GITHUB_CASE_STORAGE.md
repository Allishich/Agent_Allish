# GitHub Case Storage — минимальный протокол хранения промежуточных результатов

Цель: дать главному агенту устойчивое **проверяемое** файловое хранилище промежуточных данных кейса в приватном репозитории `Allishich/Agent_Allish`. Это инструкция по использованию доступного GitHub-коннектора, **не отдельный программный runtime**. Итоговые DOCX формируются **только для скачивания** вне репозитория.

## 1. Создание кейса и безопасность
1. Перед записью убедись, что GitHub-коннектор доступен, репозиторий **приватный** и у подключения есть доступ на запись; не предполагай наличие этих прав в чужой среде.
2. Получи разрешение пользователя на хранение материалов кейса в приватном GitHub. Пользовательские токены, пароли, контакты клиентов, сырые базы персональных данных, секретные документы и закрытые исследования **не коммить**. Храни минимизированные результаты, обезличенные вводные или безопасные ссылки.
3. Используй уникальный безопасный `case_id`: строчные латинские буквы, цифры, дефис или подчёркивание. Не допускай `/`, `..`, пробелов и специальных символов. Имя ветки: `case/<case_id>`; создание из актуального `main` **один раз**. Новое содержимое кейса никогда не пишется в `main` и не требует PR.
4. Для существующего кейса используй его ветку без создания новой. Сначала прочитай сохранённое состояние и revision из неё. Не переписывай существующие пути другого case_id.

## 2. Что писать
```text
cases/<case_id>/
  discovery.md
  brief.json
  product_strategy/
    brief.json
    state.json
    results/methods/<method_id>.json
    results/stages/<NN>_stage.json
    results/product_strategy_outline.json
    history/...
  communication_strategy/
    state.json
    results/methods/<method_id>.json
    results/stages/<Cnn>.json
    results/communication_strategy.json
    history/...
```
Пути и имена результатов уточняй по действующим `workflow.yaml` и `method_routing.yaml`; форматы по `contracts.json`. Различай M01 продуктового и M01 коммуникационного модулей.

- После содержательного сообщения интервью обновляй `discovery.md` и `brief.json`; подтверждение брифа записывай отдельной новой ревизией.
- После исполнения метода/этапа сначала записывай **все** результаты (method/stage), после них — новое `state.json` с актуальными ссылками, ревизиями и статусом `awaiting_parent_approval`.
- После настоящего согласования пользователя записывай обновлённое `state.json` и evidence этой версии. Без действительного пользовательского подтверждения не выставляй `accepted`/ `live_user`.
- При изменении подтверждённых вводных или ранее принятых этапов сохраняй историю; Git-история дополнительно позволяет проверить прежние записи. Не переписывай более свежую версию поверх старой.

## 3. Как именно записывать и подтверждать
Используй доступные GitHub-инструменты: `create_branch`, `create_file`/`update_file` (либо эквивалентные действия безопасного файлового API) **с явным ref ветки кейса**. Для обновления требуй актуальный `content_sha` (или иной механизм предотвращения перезаписи конфликтующей версии). Не используй редактирование `main`.

После каждой порции записи:
1. Проверь ответы GitHub о commit SHA и итоговом пути.
2. Повторно прочитай критические файлы `brief.json` и `state.json` из **той же ветки**; при необходимости прочитай `stage_record`.
3. Сопоставь `case_id`, `revision`, `stage_id` и ожидаемый статус; в отчёте перечисли конкретные подтверждённые файлы, ветку и commit SHA.
4. Считай `saved:true` только те артефакты, факт записи которых подтверждён. Любая ошибка, отказ доступа или частичная запись → `saved:false` для затронутых файлов, сохранение/переход не объявляй успешно завершёнными.

При невозможности записать файл предоставь его полный JSON/Markdown в чате для ручного сохранения; не выдавай гипотетический GitHub-путь за реальный.

## 4. Возобновление в новом чате
Получив `case_id`, найди ветку `case/<case_id>`, прочитай `cases/<case_id>/brief.json`, продуктовый и коммуникационный `state.json` (если соответствующий модуль инициализирован), фактические stage/method-файлы, указанные в `result_refs`, и подтверждения согласований. Не требуй несуществующий state от ещё не запущенного модуля.

Сверь ревизии, case_id, файлы и последние согласованные версии. Выведи последний завершённый и следующий допустимый этап; **не делай новый переход до положительной сверки**. При конфликте, недостающем файле или невозможности подтвердить согласие — `blocked`/запрос восстановления, не реконструируй файлы по памяти чата.

## 5. Финальные документы — вне GitHub
После S01–S07, C01–C06 и итогового quality gate сформируй два полных `product_strategy.docx` и `communication_strategy.docx` в доступной рабочей среде. Проверь реальное существование файлов и приложи/предоставь действующие ссылки для скачивания. **Не коммить DOCX** и не объявляй завершение, если пользователь не может их получить.

## 6. Что считается доказанным
Описание процедуры и успешная запись тестового файла не доказывают целостность полного кейса. Для демонстрации запусти синтетический кейс: подтверждение брифа → S01 → запись → отказ перехода без согласия → настоящее согласование → закрытие чата → проверка чтения и S02 из другого чата. В журнале разделяй `execution_mode` и флаги `persistence_verified`, `cross_chat_resume_verified`. Не отмечай `true` до фактического прохождения соответствующего теста.
