# Communication Strategy — подключаемый модуль v0.1

## Назначение и статус

Подчинённый модуль Agent_Allish для разработки **коммуникационной стратегии на основе подтверждённых вводных и продуктовых результатов**. Содержит 12 самостоятельных YAML-методик (M01–M12), шесть обязательных этапов C01–C06, протокол обмена с главным агентом и форматы результатов.

Структура **декларативная**: встроенного Python-исполнителя, API-сервера или автоматически подтверждённого долговременного хранилища здесь нет. Главный агент действует через `AGENTS.md` и либо поддерживаемую среду исполнения, либо честно обозначенный ручной режим.

## Где искать инструкции

- `MODULE.md` — назначение, границы, принцип подчинения главному агенту.
- `workflow.yaml` — C01–C06, действия, статусы, namespace хранения.
- `method_routing.yaml` — выбор базовых и условных методов.
- `methods/M01.yaml` – `methods/M12.yaml` — содержательные методики и требования к их нативным результатам.
- `handoff.yaml` — ответственность и формат передачи данных.
- `contracts.json` — JSON Schema Draft 2020-12 для входа, выхода, методов, этапов, состояния и стратегии.
- `EXECUTOR.md` — порядок исполнения и фактические проверки.
- `CONTRACT_VALIDATION.md`, `examples/`, `tests/validate_contracts.py` — примеры и проверка контрактов.

## Вход

Главный агент сначала получает подтверждённый `cases/{case_id}/brief.json` от `common_intake`. В запросе `module_request` с `action:start_case` обязательны:

- `confirmed_brief` — **полный исходный объект** общего брифа, а не устаревшая проекция `communication_context`;
- `product_strategy_outline` — реально полученный каркас продуктовой стратегии, либо явный `null`, если он пока недоступен;
- `expected_revision=0` — начальная ревизия **коммуникационного модуля**, не версия общего брифа.

Формат запроса описан в `contracts.json#/$defs/module_request` и `validation/common_intake/brief_mapping.yaml#communication_strategy`. Вложенный бриф **отдельно** проверяется по `validation/common_intake/brief.schema.json`, продуктовый каркас — по `validation/product_strategy/contracts.json#/$defs/strategy_outline`. Исполнитель дополнительно сверяет `case_id`, происхождение данных и фактические ревизии.

## Основной цикл

Последовательно выполняются C01 (диагностика), C02 (аудитория и барьеры), C03 (позиционирование), C04 (сообщения и доказательства), C05 (каналы), C06 (проверка эффективности). `run_next_stage` обрабатывает один этап. После него главный агент предъявляет результат пользователю и отправляет `approve_stage` только после согласия. На каждый этап применяются базовые методы; условные выбираются обоснованно. Недостаток данных допускает `partial`/`awaiting_data`, но не выдуманные результаты.

Доступны действия `start_case`, `run_next_stage`, `approve_stage`, `attach_human_data`, `update_brief`, `get_status`, `get_strategy`. Изменяющие состояние действия проверяют `expected_revision`.

## Результаты и хранение

```text
cases/CASE_ID/
  brief.json                                  # общий бриф (common_intake), только чтение
  communication_strategy/
    brief.json                                # локальная копия подтверждённого входа
    state.json                                # case_state
    results/
      methods/M01.json                       # method_record с native_result
      stages/C01.json                        # stage_record
      communication_strategy.json            # strategy
    history/                                  # предыдущие ревизии при наличии хранилища
```

Продуктовый модуль пишет только в `cases/CASE_ID/product_strategy/`. Нельзя выдавать `saved:true`, если запись не проверена. При делегировании записи возвращается артефакт с `saved:false` и `content`. Реальные кейсы и персональные данные **не публикуются в GitHub**.

## Границы формальной проверки

JSON Schema ограничивает структуру, типы, действия и обязательные поля. Она **не** подтверждает истинность рынковых выводов, фактический доступ к файлам, согласие пользователя, полноту методических расчётов или совпадение `case_id` между несколькими объектами. Для этого действуют дополнительные инструкции и тесты.

Методики M01–M12, `method_routing.yaml`, схема общего `brief.json` и продуктовый протокол не меняются при усилении коммуникационного контракта.

## Текущие ограничения

Это согласованная **структура протокола**, а не подтверждённый промышленный запуск. Сквозное исполнение через реальный LLM-хост, транзакционное сохранение, валидность источников и работа с реальными пользовательскими данными должны проверяться в выбранной среде.
