# Исполнение коммуникационного модуля

**Хранение:** при доступном GitHub промежуточные результаты и итоговый структурированный JSON сохраняются главным агентом по `validation/GITHUB_CASE_STORAGE.md` в приватной ветке `case/<case_id>`, только внутри коммуникационного namespace. Перед записью передавай полный content артефактов. Само отсутствие инструментов GitHub у модуля не означает, что сохранение состоялось: `saved:false` до проверенного чтения файла из ветки. DOCX создаёт и отдаёт пользователю главный агент, в GitHub их не записывают.


1. Получить от главного агента `module_request` с `confirmed_brief`: **полный исходный объект** `cases/{case_id}/brief.json` из `common_intake` без преобразования в `communication_context`. `product_strategy_outline` передаётся отдельно: фактический продуктовый `get_outline` или `null`, если результат недоступен. Не проводить повторное вводное интервью.
2. Проверить оболочку по `contracts.json#/$defs/module_request` (или корневому `oneOf`), а **отдельно полный бриф** по `validation/common_intake/brief.schema.json`. При `start_case` обязательны `interview_status=confirmed`, `user_confirmed_brief=true`, положительная ревизия, `case_id` брифа = `case_id` запроса, полное сохранение `unknowns` и `field_provenance`. Если `product_strategy_outline` не `null`, проверить, что это реальный результат продуктового модуля по его контракту, и `case_id` совпадает. При ошибке `blocked`, без создания нового состояния и без подмены данных. `expected_revision` относится к локальному состоянию коммуникационного модуля, а не к `brief.revision`.
3. Выполнять только запрошенное действие и его условные обязательные поля по `contracts.json`: `start_case` — исходный бриф, продуктовый каркас или `null`, `expected_revision=0`; `run_next_stage` — актуальная `expected_revision`; `approve_stage` — `stage_id`, `parent_approval=true` и ревизия; `attach_human_data` — `method_id`, непустые `data_artifacts` и ревизия; `update_brief` — новый подтверждённый `updated_brief` и ревизия. Прочитать сохранённое состояние до записи, проверить `case_id` и отсутствие конфликта `expected_revision`. `get_status`/`get_strategy` не изменяют состояние. Для `run_next_stage` выполнить ровно один следующий этап C01–C06.
4. Для этапа прочитать method_routing.yaml: базовые методы рассмотреть всегда, условные — только если они могут изменить решение; записать почему метод выбран или пропущен.
5. Выполнить выбранные methods/*.yaml на реальных доступных данных. Разделять user_reported, public_source, user_document, hypothesis, synthetic_example и model_calculation. Отсутствие исследований людей означает awaiting_data/partial, а не вымышленные интервью.
6. Проверять результаты: `native_result` метода — согласно обязательным `outputs.required` **прочитанной** `methods/Mxx.yaml`, внешнюю запись — по `contracts.json#/$defs/method_record`; результат этапа — по `stage_record`, состояние — по `case_state`, итог — по `strategy` (шесть этапных ссылок и минимум три альтернативы, в том числе `status_quo`). По `method_routing.yaml` сверять принадлежность метода этапу, а по `case_state` — допустимые состояния C01–C06. Сохранять собственную копию входного брифа, результат метода, результат этапа, ограничения, состояние и историю **только** в `cases/{case_id}/communication_strategy/` по `workflow.yaml`. Общий `cases/{case_id}/brief.json` принадлежит `common_intake` и доступен только для чтения; `product_strategy/` не изменять. Если реальное сохранение недоступно, вернуть артефакты с `saved:false` **и полным `content` каждого артефакта**. `saved:true` допустим только после проверенной записи.
7. Перед возвратом проверить `module_response` по `contracts.json#/$defs/module_response`: `request_id`, `action`, `case_id`, `state_revision`, `artifacts`, `data_requests`, `limitations`, `errors`, `next_action` и статус сохранения. `blocked` требует непустых `errors`; `awaiting_parent` — `awaiting_parent_confirmation=true`. После каждого этапа вернуть управление родителю для согласования. Не продолжать без `approve_stage`.
8. После C06 собрать единую стратегию, даже если отдельные этапы partial. Явно пометить гипотезы, альтернативы, продуктовые зависимости и план проверки.
9. При обновлении вводных пересмотреть только затронутые результаты и сохранить историю, если хранилище позволяет.
10. Не изменять другие каталоги, не делать неподтверждённых заявлений о запуске кода или интеграции. Проверка схемы не доказывает истинности фактов. Сопоставление разных `case_id`, актуальности `brief.revision`, продукта и коммуникационного состояния, а также статусов реального хранилища — обязанности исполнителя. Невозможность выполнить машинную JSON Schema-валидацию помечать как ограничение, а не считать результат автоматически проверенным. Для примеров и негативных проверок см. `CONTRACT_VALIDATION.md`.
