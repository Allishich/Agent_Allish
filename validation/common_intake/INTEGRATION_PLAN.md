# План согласованной интеграции в основной агент (для будущего единого PR)

**Текущие файлы GitHub не изменены.** Это предложение адресных правок после согласования общего проекта.

## Главный AGENTS.md

Сохранить: свободный вход, один вопрос за раз, последовательные уточнения, семь критериев достаточности, запрос подтверждения, недопустимость выдуманных фактов.

Предложить изменения:

1. Вместо общего `discovery.md` в корне использовать `cases/{case_id}/discovery.md`, не смешивая кейсы.
2. Добавить ссылку на `intake/INTERVIEW_MODULE.md` и `intake/brief.schema.json`.
3. Во время интервью обновлять `discovery.md` и черновик `brief.json`; после подтверждения ставить `interview_status=confirmed` и сохранять `revision`.
4. После подтверждения главный агент решает, когда вызвать `product_strategy` и `communication_strategy`, и выдаёт адаптированные представления по `brief_mapping.yaml`.
5. Не запускать методические подмодули на основании неподтверждённого черновика. Не требовать от продуктовика самостоятельного повторного интервью.

## Основная methodology.md

Сейчас включает продуктовую и коммуникационную стратегии в одном документе. Для новой модульной архитектуры перед объединением PR согласовать с владельцем основного агента, как связать её этапы с продуктовым модулем v0.2 и коммуникационным модулем; не создавать две параллельные несовместимые последовательности. Содержимое документа пока не переписывается.

## Продуктовый модуль v0.2

Контракт `start_case` уже совместим **после преобразования** по `brief_mapping.yaml`. Не передавать общий `brief.json` напрямую: его дополнительные поля не разрешены в `$defs/brief` действующего `contracts.json`. Пример `examples/product_start_case.request.json` проверяется на существующей JSON Schema.

## Коммуникационная сторона

Отдельного исходного JSON-контракта в текущем `main` нет. `communication_context.schema.json` — только предложение входа, основанное на блоке 7.3 `methodology.md`. Нужно согласовать поля и момент использования выводов продуктового исследования с Алиной. Не модифицировать её документы без согласия.

## Сохранение и приватность

`cases/` — **рабочие данные**, не предмет исходного GitHub PR. Записи пользователей, персональные данные, коммерческие документы и доступы не коммитить. Реализация долговременного хранения зависит от хоста; декларативный формат не обеспечивает запись автоматически. Версии данных остаются только при фактической возможности хранения.

## Целевая раскладка спецификаций в будущем PR (предложение)

```
intake/
  README.md
  INTERVIEW_MODULE.md
  intake_workflow.yaml
  brief.schema.json
  brief_mapping.yaml
  communication_context.schema.json
  examples/...
validation/product_strategy/...  # уже в отдельном PR, без переписывания методик
```

До команды на GitHub: работать только с архивами и файлами на Google Drive. При финальной подготовке большого PR решить судьбу уже открытого PR #3, чтобы не получилось двух конкурирующих веток и случайного merge.
